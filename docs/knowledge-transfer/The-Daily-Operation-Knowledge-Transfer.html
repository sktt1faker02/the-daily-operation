Application summary

[Code] The Daily Operation is a Microsoft Power Apps Code App built with React, TypeScript, and Vite. Payroll is the current business module. Dataverse is accessed through the Power Apps SDK client and generated services. The current routed areas include payroll administration, employee records, payroll templates, My Payroll, and payslip viewing (src/App.tsx › App; src/router.tsx › router; src/lib/power/data-client.ts › dataClient).

[Verify in environment] User role assignments, app sharing, target environment, Dataverse privileges, and the deployed version must be checked in Power Platform before making an operational change.

01 — Overview and architecture

Evidence rule. Every behavior claim below is marked [Code] and points to the source that shows it. [Verify in environment] means the repository cannot establish the live Power Platform setting. Environment-specific values are intentionally not copied into this handover.

1. What this application is

[Code] The Daily Operation is a React and TypeScript single-page Power Apps Code App. src/main.tsx mounts App; src/App.tsx composes the toast provider, TanStack Query provider, access gate, and router. The Vite build uses the Power Apps Vite plugin (vite.config.ts). The app is designed to run in a Power Apps host and also has local development commands (AGENTS.md; package.json › scripts).

[Code] The code uses the Microsoft Power Apps SDK for app context and Dataverse access. src/lib/power/power-context.ts › getPowerContext reads host-provided context; src/lib/power/data-client.ts › dataClient binds the SDK data client to generated data-source metadata. Feature services call that client. No hand-written fetch or Axios data layer was found in src.

[Code] Dataverse-backed business data is accessed through app services. The repo includes a solution project under solution/A365_DailyOperations, generated connector metadata under .power/schemas, and generated models and services under src/generated. The source tree also contains a Dataverse plug-in project under plugins/A365.Payroll.Plugins and helper scripts under scripts.

[Verify in environment] The actual environment, deployed app version, solution membership, connections, server-side plug-ins, and role assignments must be checked in Power Platform. power.config.json contains an environment binding; its identifier is omitted here because it is environment-sensitive.

4. UI, state, and data-fetching patterns

[Code] App-wide server state uses TanStack Query. QueryProvider sets queries to no retry, no refetch on window focus, five-minute stale time, and ten-minute garbage collection (src/providers/query-provider.tsx › QueryProvider). Payroll and employee hooks wrap the corresponding service calls and invalidate query keys after mutations (src/features/payroll/hooks/, src/features/employees/use-employees.ts).

[Code] zustand is listed in package.json, but no Zustand store or hook usage was found under src. Current data hooks use TanStack Query.

[Code] The UI uses React, React Router, Tailwind CSS, locally provided shadcn-style primitives built on Radix UI, Lucide icons, and Sonner toasts. TanStack Table is used for employee and payroll tables. date-fns supports date formatting. pdfmake builds downloadable payslip PDFs and is dynamically imported in src/features/payroll/payslip-document.ts › openPayslip. Recharts is a declared dependency and has a shared chart wrapper in src/components/ui/chart.tsx; no business chart usage was found in the page components inspected for this phase.

[Code] The root README.md is still the generic starter-template readme; the application-specific orientation is in docs/. No app-specific setup section was found in README.md.

[Code] Styling starts in src/index.css and is processed by the Tailwind Vite plugin configured in vite.config.ts. The route shell and visual navigation live in src/pages/_layout.tsx.

5. Tests and known documentation gaps

[Code] Vitest runs the test suite (package.json › scripts.test), with JSDOM and @testing-library/jest-dom loaded from vitest.setup.ts. The source contains 16 colocated test files: 14 under payroll, one under employees, and one under shared UI. package.json has no Playwright script or browser end-to-end test command.

[Code] Not found in code: a SharePoint data source or upload flow for payslips. The payslip code creates a PDF in the client. Do not infer that the PDF is saved to SharePoint (.power/schemas/appschemas/dataSourcesInfo.ts, src/features/payroll/payslip-document.ts).

[Verify in environment] Not found in code: a confirmed current deployment target, production URL, active connection owner, actual role configuration, or published app release status. The repository contains a deployment runbook, but its live-environment statements must be rechecked before use (docs/deployment.md).

02 — Setup and deployment

Evidence rule. [Code] statements describe files or behavior visible in this repository. [Verify in environment] statements require a current Power Platform or workstation check. This guide omits connection strings, credentials, environment IDs, organization URLs, app IDs, and solution GUIDs.

1. Prerequisites

[Verify in environment] Microsoft lists an IDE, Node.js LTS, npm, Git, and Power Apps CLI as prerequisites for Power Apps Code Apps. The target Power Platform environment must also have Code Apps enabled. Confirm these before setup in the current workspace and admin center. Microsoft Learn: Code Apps overview.

[Code] This repository has a lockfile and uses npm scripts. Its manifest declares @microsoft/power-apps-cli version 1.0.1 as a development dependency. The current inspection workstation reported Node v24.21.0, npm 11.19.0, and local pa CLI 1.0.1; these are capture-time values, not a version policy (package.json, package-lock.json; node --version, npm --version, and local pa --version).

2. First-day local checklist

  1. [Verify in environment] Obtain the repository through the team’s approved

source-control process. Start in the repository root.

  1. [Verify in environment] Install a supported Node.js LTS release, npm,

Git, and the current Power Apps CLI. Sign in and verify the intended account with pa auth login and pa auth status (Microsoft Learn: Power Apps CLI reference).

  1. [Code] Install the locked project dependencies with npm ci (the repo

includes package-lock.json). If dependency changes are intentionally needed, use the team’s package-update procedure; this handover does not change dependencies.

  1. [Code] Check power.config.json locally and confirm the configured

  1. [Code] Run npm run build to type-check and create the production web

build (package.json › scripts.build).

  1. [Verify in environment] Run the Power Apps local host with pa app run

and sign in through the host. npm run dev starts the Vite development server, but does not replace the Power Apps host integration. The CLI command is documented in Microsoft’s Power Apps CLI reference.

  1. [Verify in environment] Confirm the expected role-gated landing page

appears and that Dataverse reads succeed for a test account. Do not use real payroll data for setup checks.

[Code] The available npm scripts are dev, build, lint, preview, test, and test:watch (package.json › scripts). The project guidance also recommends pa app run, npm run build, npm run lint, and npm run preview (AGENTS.md › Development Commands).

3. How data-source code is maintained

[Code] Registered Dataverse table data sources in .power/schemas/appschemas/dataSourcesInfo.ts are: a365_departments, a365_employees, a365_hdmfcontributions, a365_payrollentries, a365_payrollperiods, a365_payrolltemplatelines, a365_payrolltemplates, a365_philhealthcontributions, a365_positions, a365_ssscontributions, a365_taxbrackets, roles, and systemusers. The same registration also contains the whoami Dataverse API operation. Generated models and services are under src/generated/models/ and src/generated/services/.

[Code] Feature services use the shared SDK client in src/lib/power/data-client.ts › dataClient. Generated files are output from the Power Apps CLI and must not be edited by hand (AGENTS.md › Dataverse Rules; generated-file headers).

[Verify in environment] To add an existing Dataverse table, confirm its logical name in the intended environment first, then from the app root run:

npx --no-install pa app add data-source --connector dataverse --table <table-logical-name>

To refresh generated metadata for a registered source, use:

npx --no-install pa app refresh data-source --name <data-source-name>

These are current CLI command forms documented by Microsoft. The CLI writes generated schema/model/service artifacts, so review the diff and rebuild afterward. Microsoft Learn: CLI reference and Connect a code app to Dataverse.

4. Build and publish to Power Apps

[Code] For a development publish, the repository deployment runbook shows building first and then using pa app push. It also documents adding the app to a solution with --solution-id (docs/deployment.md › Step 1 and Updating an existing release). The general syntax is:

npm run build
npx --no-install pa app push --solution-id <solution-guid>

[Verify in environment] A push publishes to the active Power Apps environment/account. Before running it, check the local power.config.json, the active CLI account/environment, intended solution, app sharing, and release approval. Publishing changes the app in that environment; this document phase does not run a push. Microsoft documents pa app push as the publish command in its CLI reference.

[Code] docs/deployment.md describes a managed-solution path: publish the Code App into the solution, export the solution as managed from development, select the intended target environment, import the solution, then perform environment-specific configuration and a smoke test. Its sample commands use pac solution export, pac auth select, and pac solution import.

[Verify in environment] Treat that runbook as a starting point, not proof of the current solution state. It contains a statement that the Code App was missing from the solution when written. Confirm current solution membership, version, target environment, connections, table data, role assignments, and deployment approvals in Power Platform before following it. No environment identifiers or URLs are reproduced here.
